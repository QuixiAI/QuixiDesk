# Claude desktop UI exploration for QuixiDesk tests

The reference application inspected through computer use was **Claude for Mac 4.29.0 (260974)**. Its About window displayed a build timestamp of Oct 27, 2026, 1:57 AM. This is a different build from QuixiDesk's bundled renderer baseline. The observations below identify additional user-facing contracts to test, not functionality already implemented or validated in QuixiDesk.

The resulting expansion adds **73 cases** to the original 170, for **243 cases** in total, and adds five detailed specifications. The additions comprise 20 Core, 49 Conditional and four Policy cases. The original 24-case smoke selection remains unchanged.

Exploration used the native app's accessibility tree and screenshots. Menus, tabs, empty states and unsaved forms were opened interactively. No chat prompt was submitted, file uploaded, task/project created, connector authorized, plugin installed, recording started, notification preference changed, or account/system setting changed. Native context pickers and unsaved forms were cancelled. The app was left on the main New session screen with menus closed.

Private conversation contents, account identifiers, local filenames, device names, credentials and screenshots are deliberately omitted from this document. The observations retain only product controls and generic behavior needed to design fixture-based tests.

## How these observations change the test plan

The [main plan](E2E_TEST_PLAN.md#claude-ui-exploration-additions) adds cases with three scope labels:

- **Core:** a correctness boundary for existing app concepts, such as preserving an unsaved form when a nested native picker is cancelled.
- **Conditional:** acceptance coverage for a feature only when QuixiDesk implements or advertises it. Missing functionality is a visible capability gap, not a passed or silently skipped test.
- **Policy:** the desired behavior must first be chosen and documented, such as whether browser logins are shared across sessions or whether Manual offers per-action approvals. Test the chosen contract rather than copying reference wording.

The proposed failure variants are test designs derived from observed controls. This exploration did not verify their backend outcomes. For example, a GitHub-event menu item establishes a UI entry point, not webhook delivery correctness; a “Shared with you” tab establishes an ownership surface, not access-control correctness.

Use fixture accounts, repositories, calendars, notification sinks, microphones/audio samples and target apps when implementing these cases. Never use a personal account's real conversations, notifications, connected services or repository branches as the test data.
